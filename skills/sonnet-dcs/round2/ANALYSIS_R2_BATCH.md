## Gate reliability (cp3 "current active" read with versions but none active)
d1a-core hold rate 5/7 runs (5/6 when the skill was actually loaded in cp3). Held: d1a x2, d2a, d2d(gate), d2e; each curled state (b) and saw version 0 before shipping. Failures had different causes, neither lever-text distraction: d2b: the Skill was never invoked in cp3 (23 of 24 sessions invoked it as call 1-2) -> behaved like no-skill (404 + null sentinel), trigger noise. d2c: skill loaded but the verify curl of state (b) was never run; code widened the not-found condition (the "widen Y" error rule 1 forbids); the alias lever's extra verify clause may have crowded it out (n=1). d2d's collapse (cp3 47/76) is harm from its lever: the ordering line "identity existence -> always preconditions -> ..." made a policy-set call require an existing identity, so the tests that set policy first got 404 and everything downstream cascaded (~-25 tests). Length is not the signal.
Make it deterministic: (1) gate as the FIRST section, a two-line invariant: for an identity that exists every "current value" read succeeds; not-found means the identity is missing, nothing else; numbering starts at 1 so "nothing yet" is integer 0, emitted by reads and accepted by writes. (2) tie verify to the summary: "state what the current-value read returns for an identity that exists with nothing set yet". (3) imperative description: "Invoke before reading any code...". (4) no lever-specific verify clauses.
